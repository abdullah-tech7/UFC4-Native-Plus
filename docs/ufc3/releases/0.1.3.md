Native EA SPORTS UFC 3 port (PS4 `CUSA06534`, update 1.14) for Windows and Linux.
**No game files are included**: you need your own dump of the game and its 1.14 update.

The user tested these changes on **Linux with an RTX 4070** and **Windows with an
RTX 3060 Laptop**. The AMD fixes also come from **@luscamovi's RX 9070** testing;
individual AMD cases and the separate Windows write-window reports are identified below.
These are reported gameplay results, not new gameplay tests performed while preparing this
release. Technical provenance is recorded in [`gpu/VENDOR.txt`](../../../gpu/VENDOR.txt),
the [backport report](../MANCELLI-BACKPORT.md), the [career crash report](../UFC-8-HOST-SIGSEGV.md)
and the [performance handoff, section 17](../GROK_HANDOFF.md).

### Fixes

- **Career is saved.** Previously, starting a career could display "Your career data will
  not be saved due to an error" or "An error has occurred while saving". The game mounted
  `CAREERSAVE0` for reading and writing without explicitly asking to create it, so a new
  career failed with `NOT_FOUND`. `src/runtime_savedata.c` now creates a missing save for
  that read-write mount, logs every failing save call, and implements `sceSaveDataLoadIcon`:
  it returns the save's icon, falls back to `/app0/sce_sys/icon0.png`, then to a built-in
  1x1 PNG if neither exists. `src/runtime_file.c` also creates `temp0/createplayer` and
  `temp0/images/{career,match}`, which the game expects to open without creating first.
  These are automatic fixes with no launcher toggle or `BB_*` switch. Local commits:
  `2fb02a3`, `327737c`, `dcde0dd` (plus `11906cd` for the failure-log buffer size).
  Career saving was tested on Linux RTX 4070 and Windows RTX 3060 Laptop; @luscamovi
  supplied the career-save patches from the AMD RX 9070 work. Saving successfully does
  not yet verify the career pause-menu portrait; see Known issues.

- **Career no longer crashes on entry.** A pre-existing runtime import had the wrong
  signature: `sceKernelConvertLocaltimeToUtc` took four arguments instead of five.
  When the game's `mktime` passed `tm_isdst=-1` as the second argument, the runtime
  treated it as an output pointer and wrote to `0xffffffff`, causing a host SIGSEGV
  on Linux. `src/runtime_kernel.c` now accepts the missing integer argument so that
  all three output pointers occupy the correct positions (`5ba1246`). This is an
  automatic ABI correction, not a GPU workaround and not a regression introduced by
  the shader backports. Career entry was tested on Linux RTX 4070 and Windows RTX
  3060 Laptop; the address-level diagnosis is documented in the career crash report.

- **Hair has coverage instead of square cards.** Previously, hairstyles appeared as
  flat, hard-edged rectangles because the renderer ignored `DB_ALPHA_TO_MASK`.
  The fragment shader now converts alpha into a hardware-style 2x2 dither pattern,
  including on MSAA targets, and applies to every draw that sets the register: hair
  and beards in Create Fighter and in fights alike (`06d0b6b`). A dark torso seen
  during development came from the created fighter's broken skin under the hair
  layer, which the skin fix below resolves. This adapts mancelli's `69ab1996` in the
  shader exporter, Vulkan pipeline/cache and runtime info; local refinements select
  the plain shader first and the dither variant only for draws that actually need it.
  The fix is on by default. `BB_ALPHA_TO_MASK=0` disables it; `=coverage` uses Vulkan
  alpha-to-coverage on multisampled targets; `=colourmap` limits it to draws sampling
  the runtime `8_8_8_8` sRGB hair colour map (Create Fighter only).
  Diagnostic controls `BB_ALPHA_TO_MASK_SKIP=<ps-hash>,...` exclude pixel shaders,
  and `BB_ALPHA_TO_MASK_DRAWS=<index-count>,...` select draws (negative entries exclude
  them). Hair, beards and torso were checked on Linux RTX 4070 in Create Fighter
  (repeated hairstyle changes) and in career fights.

- **Created-fighter skin survives repeated editing.** Changing hairstyles or skin
  tones several times used to leave black or garbled patches. The game compresses
  these textures on the GPU: the texture cache now tiles an uncompressed storage
  image into the memory/buffer-cache path before uploading its block-compressed
  view, and writes back overlapping storage images before creating that view.
  Compatible skin texture views requesting more mip levels or layers now expand
  the cached image instead of discarding it. This is the partial backport of
  mancelli's `01b32f45` in `video_core/texture_cache` (local `5875804`, parts 1, 2 and 4).
  `SHADPS4_BC_MODE=3` is the default; `=0` restores the older compressed-view/copy and
  storage-alias behaviour for comparison. The compatible-view expansion remains
  automatic. There is no launcher checkbox. The fork's CPU-write fault flush and
  dispatch-level `StorageImageSync` were not imported. Skin editing was tested on
  Linux RTX 4070 and Windows RTX 3060 Laptop; keep pre-upload and write step off
  as described under Defaults changed.

- **Shadows use the right depth representation and release their temporary copies.**
  Emulating guest Z16+S8 with a host 24/32-bit depth format previously made the
  constant depth bias too small, causing shadow acne or flicker. `vk_rasterizer.cpp`
  now scales it according to the actual host format: x256 for the emulated formats,
  x1 for real D16. This adapts mancelli's `c08218db` (local `25998f2`) and respects
  `BB_Z16S8_AS_D16=1`, the launcher/run.sh default; `=0` requests the other depth/stencil
  path. The bias correction itself is automatic. A shader reading 32-bit depth as
  `R32_UINT` now receives a colour copy containing the original float bits, rather
  than an invalid depth-as-colour view. Copies are keyed by image identity and freed
  with their source image, ending unbounded growth; replaced per-layer source views
  are also destroyed, fixing a smaller view leak. Those parts of mancelli's
  `72251298` are local `aa4bd2b`, with no separate toggle. Shadows were checked on
  Linux RTX 4070 and Windows RTX 3060 Laptop; AMD's layer-view corrections are below.

- **Colour metadata no longer leaves untouched MSAA layers undefined.** Pending fast
  clears are now applied when FMASK is decompressed. Previously, an MSAA image the
  GPU had never drawn to could escape clearing, allowing stale skin or dot-grid
  data to appear when layers such as tattoos were resolved. `vk_rasterizer.cpp`
  now clears those images too. Sources: upstream `14ada48a` / PR #5283 by Claudio
  Godoi (local `631f49f`) and the MSAA portion of mancelli's `789551b0` (local
  `58b2425`). These fixes run automatically; the fork's `SHADPS4_FMASK_DECOMPRESS`
  switch was not imported. Create Fighter was tested on Linux RTX 4070 and Windows
  RTX 3060 Laptop; the stale-fighter/dot-grid failure mechanism is documented in
  the backport report rather than a claim that every such artifact was reproduced
  on each card.

- **Shader recompilation follows GCN more closely.** Incorrect floating-point and
  execution semantics could corrupt shading, propagate NaNs into black areas, or
  select the wrong per-instance data. These backports in `shader_recompiler` and
  Vulkan blending are automatic, with no launcher or per-fix `BB_*` toggle:

  - GCN NaN handling for legacy instructions, unordered comparisons, `DX10_CLAMP`
    and `med3`: TheTurtle's `c4952908` / #5257. mancelli's `5dedb48f` also preserves
    the full 256-register count instead of truncating it to zero.
  - NaN-aware 32/64-bit min/max: mancelli's `02d3b06d`, using `NMin`/`NMax` so the
    non-NaN operand survives as on GCN. The report identifies Intel Arc as a motivating
    case; no new Intel test is claimed here.
  - Correct clamp/legacy handling for `V_RCP`, `V_RSQ` and `V_LOG`: DanielSvoboda's
    `1c2b8f97` / #5346, preventing incorrect exceptional results in shader maths.
  - Preserve the active-lane `EXEC` scope after an empty branch: artemkaVG's
    `c34ca21f` / #5220, so later instructions execute for the correct lanes.
  - Unbiased instance IDs for every use, and step rates with a base instance:
    TheTurtle's `7721a1ef` / #5260 and Chris Chreece's `10393d2c` / #5274.
  - Correct `ZERO`/`ONE` blend factors with `MIN`/`MAX` blend operations:
    kiwakiwaa's `c5dd8b8b` / #5197, preserving the intended layer composition.
  The resulting build was gameplay-tested on Linux RTX 4070 and Windows RTX 3060
  Laptop; these are correctness fixes, not individually isolated before/after
  visual claims on every GPU. **The first launch rebuilds the shader cache** because
  the generated shaders, metadata and pipeline keys changed. Expect compilation
  work again on that launch.

- **AMD RDNA floor and depth/stencil fixes.** @luscamovi's RX 9070 showed grain and
  black blocks on the octagon floor even after the earlier per-layer shadow fix.
  Three driver-sensitive paths are corrected:

  - Subgroup memory fences around LDS stores preserve GCN's expected ordering.
    The floor's parallel scan had effectively restarted every 16 lanes because
    the AMD compiler reordered shared-memory accesses (`82b8396`, SPIR-V shared
    memory emitter). Enabled by default; `BB_LDS_ORDER=0` disables it for comparison.
    Clear the shader cache when changing this setting.
  - BC5 images that the driver rejects with storage usage/block-texel views are
    retried without those unsupported flags, rather than created with undefined
    contents (`45fd5b0`, texture-cache `image.cpp`). Automatic, no toggle.
  - Each depth-to-colour layer conversion uses its own 2D depth view instead of
    passing a 2D-array view to a `texture2D` shader (`54e5471`). With
    `BB_Z16S8_AS_D16=1`, host images and pipelines consistently use D16, including
    on AMD drivers advertising partial D16S8 support (`338222e`, `vk_instance.cpp`).
    `=0` disables that D16 override; the 2D-view correction remains automatic.
  These cases were diagnosed and tested on AMD RX 9070 by @luscamovi. The user also
  tested the resulting release changes on Linux RTX 4070 and Windows RTX 3060 Laptop;
  that does not imply the AMD-specific failures occurred on NVIDIA.

### New features / improvements

- **PS4 Pro mode at 1080p.** Previously, enabling the game's Pro path produced a
  black screen with sound. The buffer cache now treats CMask reads as uncompressed
  (`0b289ce`), allowing the frame to render. Check **PS4 Pro mode** in the Windows
  launcher or set `BB_NEO=1`; uncheck it or use `BB_NEO=0` for the regular 900p path.
  The checkbox now controls the exported value instead of having Pro forced off
  (`83b1f3a`). @luscamovi enabled and tested this on RX 9070; the user tested it on
  Linux RTX 4070 and Windows RTX 3060 Laptop. The 4070 reaches about **80 FPS in
  fights at 1080p**; this is separate from the regular-mode write-window numbers.

- **90 FPS and stable saved limits.** The Windows launcher's FPS selector now offers
  90 alongside 60, 120, 144, 240 and Unlimited. Previously, there was no 90 option,
  and storing the list index made settings vulnerable to a new item shifting the
  choices. `sacredfire_launcher.c` now saves `fps_limit=` by value and maps legacy
  `fps_mode` indices to the matching limit (`99c64b2`, @luscamovi). Select a limit
  in the launcher or set `BB_FPS_LIMIT=90`; `=0` removes the cap. An inherited
  environment value takes precedence over the launcher. Tested on Windows RTX
  3060 Laptop; the equivalent environment limit was covered by Linux RTX 4070 testing.

- **Windows Game language selector.** Players previously needed a `.bat` setting
  `BB_LANGUAGE` to select another game language. The launcher now offers 12 entries:
  English (US), French, German, Italian, Spanish (Spain), Spanish (Latin America),
  Portuguese (Brazil), Portuguese (Portugal), Polish, Russian, Japanese and Chinese
  (Traditional). Portugal is listed but has no shipped text; use Brazil instead.
  `sacredfire_launcher.c` saves the language ID in `sacredfire.ini` and exports it
  (`e17fae2`). Choose **Game language**, or supply `BB_LANGUAGE` before starting
  the launcher to override the selection; remove the override to use the saved
  choice. This Windows feature was tested on RTX 3060 Laptop; Linux RTX 4070
  continues to use `BB_LANGUAGE`. pvict's GitHub report motivated the selector.

- **Windows memory statistics in frame stats.** The periodic log now includes the
  process working set and private bytes, making memory growth visible alongside
  FPS and GPU/readback statistics (`d37c6e0`, `videoout/driver.cpp`). Previously,
  these Windows memory figures were absent. Enable **Frame stats** in the launcher
  or use `BB_FRAME_STATS=1`; disable the option or use `=0` to stop the periodic
  stats. Verified in the Windows RTX 3060 Laptop testing. Linux RTX 4070 testing
  uses the existing Linux statistics path; these two counters are Windows-specific.

### Performance

Write windows avoid repeated GPU readback waits when the CPU writes beside GPU-owned
bytes on the same page. Instead of waiting for each write, the page manager snapshots
and opens the page until the next graphics/compute submission, then protects it again
and uploads only changed CPU words, skipping the GPU-owned words. The mechanism is
already present; this release enables `BB_WRITE_WINDOW=1` by default on both Linux
(`run.sh`) and Windows (launcher) for performance.

On **Linux RTX 4070**, regular-mode fights go from **105–113 to roughly 140–190 FPS**
(the detailed handoff records 137–196 FPS uncapped), with readbacks falling from about
380 to 120 per second. The user played **20-minute Linux sessions without a crash**.
Set `BB_WRITE_WINDOW=0` to compare with it disabled; `=1` enables it. Lift the frame cap
with `BB_FPS_LIMIT=0` when comparing throughput. These are measured configuration-specific
results, not a Windows RTX 3060 Laptop or AMD performance claim. Pro mode's 1080p result
is about 80 FPS on the 4070, as described above.

An open page can expose the previous submission's GPU bytes to a CPU read. Windows
reports on RX 9070 and RTX 4090 showed guest heap free-list corruption after a fight,
ending in a guest fault at `0x1262a2a`. That investigation remains open. Write windows
are enabled by default on both platforms; set `BB_WRITE_WINDOW=0` before starting
the launcher to disable them. See Known issues below for logging and the Windows
workaround. The reported Linux sessions do not establish that every possible
write-window failure is ruled out.

### Defaults changed

- **`BB_PREUPLOAD=0` and `BB_WRITE_STEP=0` on both platforms.** Background pre-upload
  and single-stepped writes caused black or garbled created/career-fighter skin.
  The Windows launcher and Linux `run.sh` leave both off; the skin fixes were tested
  with these settings on Linux RTX 4070 and Windows RTX 3060 Laptop. Set the respective
  variable to `1` before launch to opt back in for diagnosis, or `0` to keep it off.
  The texture-cache backport does not turn these mechanisms back on.
- **`BB_WRITE_WINDOW=1` on Linux and Windows.** Linux `run.sh` and the Windows launcher
  enable the faster path for performance (RTX 4070 fights: 105–113 to roughly 140–190 FPS).
  Windows crashes after a fight (RX 9070, RTX 4090) remain under investigation; see
  Known issues below for logging and how to disable it. Neither pre-upload nor
  write step changes with it. Explicit environment values override the defaults;
  there is no dedicated write-window checkbox. The Python launcher does not export
  its own `BB_WRITE_WINDOW`, so no Python change is required.

### Known issues

- **Write windows on Windows:** crashes after a fight remain under investigation
  (RX 9070, RTX 4090 and RTX 3060 reports with 0.1.2, corrupted guest heap free list,
  `0x1262a2a`, usually while the second fight loads). 0.1.3 keeps write windows on but
  turns write step off, a combination none of those reports used. If this
  happens, enable **Frame statistics** in the launcher and send us the session's `.log`
  from `C:\Users\<user>\AppData\Local\UFC3Native\logs` (**Open logs folder**).
  The launcher saves logs automatically. To avoid the crash, launch with
  `BB_WRITE_WINDOW=0`, for example from a `.bat` with `set BB_WRITE_WINDOW=0` before
  starting the launcher. Windows RTX 3060 Laptop release testing does not establish
  that the issue is resolved on that machine.
- **Career portraits and post-fight screen:** the player's own career fighter does not
  appear on the post-fight menu (the opponent does), and the portraits the game captures
  for career menus (`temp0/createplayer/cap_*`) come out blank or garbled. Under
  investigation; it does not affect saving or fights.
- **Long hairstyles:** some leave a slightly lighter line at the base of the neck.
- **Portuguese (Portugal), `BB_LANGUAGE=7`:** the game has no text for this language,
  even though the launcher lists it. Select Portuguese (Brazil), `BB_LANGUAGE=17`.
- No online play yet; this release does not change the online implementation.
